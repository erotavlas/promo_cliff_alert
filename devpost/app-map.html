App Map

A subscription tracker that warns you when a promo price is about to end and helps you negotiate a better one. Snapshot of source commit c0b0eb1; files move over time, so search for the names below rather than trusting line numbers.

What the app is

A mobile-sized Next.js app. You add subscriptions (internet, TV, mobile lines, streaming, software and so on). The home screen floats the ones whose promo ends within 30 days to the top, and shows the monthly and yearly jump in price. From a subscription you can see what other customers negotiated, then generate a phone script that cites a chosen result.

  • Your list lives in the browser (localStorage); there is no database or account.
  • Sample negotiation results are a seeded JSON file, labelled as sample data in the UI.
  • Gemini (server-side only) structures a plan description into features and writes the call script.

One action, end to end: "Create script"

Reference route (3 stops)

A reference route, not one you toured. Open each file and search for the anchor.

  1. The screen asks, and has a fallback

    components/ScriptView.tsx → search generate = useCallback. It fetches /api/script; on any failure it calls templateScript(req) and shows a note, so the screen is never empty.

  2. The route validates the request

    app/api/script/route.ts → POST. It checks the body with ScriptRequestSchema (from lib/scriptTypes.ts) and returns a generic 502 on failure, with no details, because the request carries personal subscription info.

  3. The model call is validated, not trusted

    lib/llm.ts → generateJson asks for JSON matching a schema (responseJsonSchema), then schema.parse(...) checks it. describeScriptRequest builds the prompt from stored facts only; SCRIPT_SYSTEM holds the rules ("do not invent prices").

A practice to reuse

Treat model output as untrusted input, and keep a non-AI fallback.

Here: generateJson in lib/llm.ts parses the reply against a schema before the app uses it, and templateScript in lib/templateScript.ts fills in the same sections when the call fails, so the user never meets an empty screen. On another LLM feature, define the output schema first, validate on the server, and decide what the screen shows when the call fails before you write the prompt.
